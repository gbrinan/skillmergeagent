스킬을 더 만들지 않고, 있는 스킬을 한 줄기(또는 갈림길)로 엮어 처음부터 끝까지 위임되게 한다.

## Goal

통폐합이 끝나도 스킬이 여럿 남는다. 서로 다른 일을 하지만 같은 업무, 같은 표, 같은 트리거를 공유한다. 이것들을 따로 두면 사람이 매번 순서를 기억하고 손으로 넘겨야 한다. `weave`는 그 스킬들을 덮는 워크플로우를 만든다. 출력이 입력으로 이어지는 자리는 잇고, 판단기준이 갈리는 자리는 갈림길로, 사람이 판단하는 자리는 정지 지점으로 적는다. 직선이면 스킬팩, 갈림길이 있으면 에이전트다. 둘 다 유효한 산출물이고, 이름만 정확히 붙인다.

## Workflow

1. 재료: 요청·대화와 기획서, 있으면 스킬 카드와 남은 스킬. 목적·시작/입력·결과가 부족하면 `askflow`로 필요한 결정 하나씩 채운다. 그 스킬이 없으면 직접 초안을 제안하고 한 질문씩 묻는다. 스킬이 없어도 단계 담당을 사람/미구현으로 표시해 설계할 수 있다. 확인되지 않은 능력을 실행 가능한 스킬로 만들지 않는다.
2. **맥락 군집**: 트리거·입출력·최종 산출물 기준으로 스킬을 묶는다. 한 군집이 한 워크플로우 후보다. 군집이 둘 이상이면 기획서에 별도 흐름과 관계를 적고, 실행 팩을 요청한 경우에만 팩을 나눈다.
3. **연결**: `A.outputs ∩ B.inputs`는 A→B의 후보 근거다. 의미와 필수 입력의 공급처, 선후 조건이 맞는지 확인한다. `outputs`·`inputs`·`next`가 없는 스킬이면 `python3 check/flow.py <폴더>`의 간선을 쓴다. 단, 확인표 C에서 사람이 확인한 것만 `chain`에 넣고, 확인 전인 `(추정)` 간선은 기획서 4절에 "추정, 미확인"으로 남긴다. 추정인 채로 계약에 들어간 간선은 거짓 계약이다. 이름이 표기만 다르면 계약 페이로드 정본으로 통일한다. 연결이 안 되는 자리는 지어내지 않고 `askflow`의 순서 빈틈 질문으로 넘긴다.
4. **갈림길**: 판단기준이 둘 이상의 경로를 낼 때만 갈림길을 그린다. 계약에는 `chain: A -> B -> D; A -> C -> D`처럼 `;`로 경로를 나눠 적는다. 순서가 매번 같으면 직선으로 두고 "순차 실행"이라고 이름 붙인다. 같은 일을 하는 스킬 둘(합침 후보)의 `next`가 서로 다른 것은 갈림길이 아니라 미결이다. 한 자리로 두고 어느 `next`가 맞는지 `askflow`에 넘긴다. 평가에서 이것을 `;` 경로 둘로 그린 적이 있다.
5. **정지 지점**: 사람 판단과 입력 누락/실패 시 멈출 자리를 기획서에 적는다. 실행 팩에서는 중간을 포함해 `사람고유` 스킬 전부를 `halt_at`에 반영하고 기존 끝점 기록·발송 검사를 적용한다. 검수가 없는 설계의 영향은 설명하되 사용자의 위험 수용을 지어내지 않는다.
6. **산출**: 기본은 `agent-plan.md` 하나에 단계 표(담당·입력·행동·출력·다음 조건), 분기/예외/정지, 완료 기준, 환경과 미결을 적는다. 새 단계는 추정으로 확인받으며 하위 호출은 부모 안에, 병렬은 합류 조건과 함께 적는다. 기존 스킬마다 사용 단계·하위 호출·범위 밖·미결 중 하나를 표시해 누락과 의도적 제외를 구분한다. 실행 팩·계약을 요청했거나 기존 팩을 수정할 때만 계약과 8절 기획서·사분면 배치를 갱신한다. 계약은 표현 가능한 확정 순서만 담는다. 병렬·하위 호출·반복이 `chain`으로 표현되지 않으면 임의로 직렬화하지 않고 기획서에 보존하며 팩 실행은 보류한다.
7. `mergechk`로 설계를 검토한다. 스킬이 없으면 직접 필수 입력 공급처·단계 담당·분기/예외·정지·완료 기준을 대조한다. 실행 팩은 계약 유무와 관계없이 계약 게이트와 기존 흐름 정합 검사를 적용한다. 기존 팩의 계약·필수 파일 누락은 RED이며 설계 모드로 낮춰 우회하지 않는다. 점검 도구가 없으면 같은 기준으로 직접 판정한다. 필요한 값이 미확인이면 초안, 모두 정해지면 설계 완료이며 실제 업무를 돌리기 전에는 실행 미검증이다.
8. `planning/`이 있으면 체인과 정지 지점 결정을 `findings.md`에 적는다(`planfiles`).

## Rules

산출물을 전달하기 전에 생성 후 정리 훅이 설치돼 있으면 `docs/post-generation-hook.md`에 따라 실제 세션 ID와 이번 생성 파일만 등록한다. 재검토 중에는 재등록하지 않는다. 훅이 없으면 불필요함·중복 사실을 한 차례 감사하고 수정안 승인 뒤 반영한다. 훅의 의미 판단 정본은 `docs/refine-agent.md`다.

- 스킬을 추가하지 않는다. 빈 자리는 `(미정)`으로 남기고 인터뷰로 채운다. 새 스킬이 정말 필요하면 그 이유(어느 사람이 무엇을 손으로 하고 있는가)를 먼저 적는다.
- 표당 기록자는 하나다. 체인 안에서 같은 표에 둘이 쓰면 `skillmerge`나 팀 결정으로 돌려보낸다.
- 중간 정지를 빠뜨리지 않는다. 끝점만 검사하는 점검기는 중간의 사람 판단을 못 본다.
- 갈림길은 판단기준을 근거로 그린다. 편의로 갈림길을 만들지 않는다.
- `mesh/` 사분면은 만들지 않는다. 소규모 팀에서 다관점 검증은 별도 스킬이 아니라 동작 테스트의 상호 검증과 다른 팀의 피드백으로 한다.
- 순서를 지어내지 않는다. 앞뒤가 파일에서 확정되지 않으면 묻는다.

## Verification

끝내기 전에:

1. 제공된 모든 스킬이 사용/하위 호출/범위 밖/미결로 설명됐고, 목적에 필요 없는 스킬을 억지로 잇지 않았다.
2. 단계별 필수 입력의 공급처와 다음 조건이 맞다. 실행 팩은 추가로 `chain`의 이름·시작점·도달성·무순환을 검사했다.
3. 사람 판단 지점이 흐름에 전부 있고, 실행 팩이면 `halt_at`에도 반영됐다. 설계만으로 발송·기록을 실행하지 않았다.
4. 산출물 유형(스킬팩 순차 실행 / 에이전트 갈림길 있음)이 근거와 함께 이름 붙었다.
5. 연동 맵에 다른 군집·에이전트와의 관계가 적혀 있거나 "현재는 독립"으로 확정됐다.
