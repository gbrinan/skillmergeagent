# 통합 점검 기준 (mergechk가 보는 것)

**성공 조건**: 기존 스킬의 맥락이 충분히 반영되면서도, 맥락 충돌과 일관성이 깨지지 않고,
하나의 일을 처음부터 끝까지 위임할 수 있는 워크플로우로 통합되어야 한다.

이를 게이트 하나와 레이어 넷으로 분해한다. L0~L3과 L4 일부는 `check/`의 스크립트가 기계적으로 판정하고,
L4의 나머지는 사람(또는 AI 리뷰어)이 시나리오를 실제 실행해 판정한다. 스크립트가 없는 환경에서는 이 문서를 체크리스트로 쓴다.

## L0: 계약 준수 게이트 (`check_contract.py`, 점검기보다 먼저)

각자 만든 스킬은 표 이름·페이로드 이름·임계값이 서로 어긋난다. 그 상태로 점검기를 돌리면 실패가 쏟아질 뿐 아니라,
이름이 어긋난 탓에 **진짜 충돌이 가려진다** (두 사람이 같은 표에 쓰는데 `견적_비교표`와 `견적비교표`로 적으면
단일 기록자 검사가 다른 표로 보고 통과시킨다). 그래서 게이트가 이름을 정본으로 맞춘 뒤 점검기가 구조를 본다.

`CONTRACT.md`의 ```contract 블록(tables · writers · chain · payloads · threshold · halt_at)과 대조한다.

| 판정 | 뜻 | 처리 |
| --- | --- | --- |
| 🟢 GREEN (0) | 위반 없음 | `--run-check`를 주면 곧바로 점검기 |
| 🟡 YELLOW (1) | 표기 변형뿐 | `REMEDIATION.md`에 치환안 → 사람이 확인·반영 후 재검사 |
| 🔴 RED (2) | 팀 결정 필요 (기록자 중복, 계약에 없는 표·이름, 임계값 상충, 체인 밖 스킬, 정지 지점의 확인 문구 누락) | 자동 교정하지 않음. 팀이 정하고 재검사 |

RED가 하나라도 있으면 YELLOW 교정안을 만들지 않는다. 이름부터 고쳐도 소용없기 때문이다.

**정지 지점(halt_at)은 체인 중간도 검사한다.** 사람 판단이 체인 중간에 있을 때 그 지점의 확인·정지 문구가 통째로 빠져도
L4는 끝점만 보므로 통과시킨다. `halt_at: 중간판단스킬, 끝스킬`처럼 전부 적으면 게이트가 다 본다.

## L1: 구조 (패키징이 규격을 지키는가)
- [ ] 필수 파일: `README.md`, `agent-plan.md`, `AGENTS.md`, `skills/`, `data/`
- [ ] 각 SKILL.md에 기계가 읽을 frontmatter: `name`, `inputs`, `outputs`, `reads`, `writes`, `next`
- [ ] `agent-plan.md`가 팩 안에 하나만 (SSOT 유일성)

## L2: 맥락 반영 (기존 스킬의 맥락이 살아있는가)
- [ ] 모든 스킬이 `agent-plan.md`나 `AGENTS.md`에 언급된다 (기획서가 모르는 스킬 = 반영 안 된 맥락)
- [ ] 각 스킬이 읽고 쓰는 표가 기획서 3절 데이터 명세 또는 계약 tables에 있다 (명세 밖 데이터 = 누락된 맥락)
- [ ] 스킬 본문이 비어 있지 않다 (헤더만 있는 스킬 = 맥락 소실)

## L3: 맥락 충돌·일관성 (합쳤을 때 서로 싸우지 않는가)
- [ ] **단일 기록자**: 같은 표에 쓰는 스킬이 둘 이상이면 실패
- [ ] **흐름 정합**: 시작점 1개, 모든 스킬에 도달(고아 없음), 순환 없음, `next`가 실재하는 스킬, 앞 스킬의 outputs와 뒤 스킬의 inputs가 이름까지 일치 (갈림길은 허용)
- [ ] **용어 일관**: 표 이름 문자열이 파일마다 다르게 쓰이지 않는다
- [ ] **규칙 일관**: 임계값(±N%)이 기획서·AGENTS·스킬에서 같은 값

## L4: 처음부터 끝까지 위임 (End-to-End)
- [ ] 체인의 시작 입력 = 기획서 4절 시나리오의 입력, 체인의 끝 출력 = 시나리오의 산출물
- [ ] 끝점이 자동 발송·기록하지 않고 사람 확인에서 멈춘다 (기계 판정: 끝점 writes 없음 + 확인 요청·정지 문구)
- [ ] **[사람 판정]** 시나리오를 실제로 한 번 실행: 선언된 정지 지점 외에 사람 개입이 없었는가
- [ ] **[사람 판정]** 틀린 입력을 일부러 넣었을 때 실제로 멈추는가

### 수용된 위험 (⚠️)와 실패의 구분

| | 판정 | 뜻 |
| --- | --- | --- |
| `DECISIONS.md`에 `결정됨` 기록 + 기획서에 위험 명시 | ⚠️ 수용된 위험 | 실패로 세지 않는다. 다만 출력에서 사라지지 않는다 |
| 기록 없음 | ❌ 실패 | 모르고 빠뜨린 것으로 본다 |

## 산출물 유형: 탈락이 아니라 이름 붙이기

| 흐름 | 산출물 유형 |
| --- | --- |
| AI 태스크(자동+증강) 3개 미만 | 팀 스킬팩 (다단계성 기준선 미충족) |
| 순서가 매번 같음 | 팀 스킬팩 (순차 실행) |
| 갈림길 있음 | 팀 에이전트 (갈림길 있음) |

직선이라고, 태스크가 적다고 탈락시키지 않는다. 만든 스킬이 그대로 에이전트의 부품이 되기 때문이다.
`human: 자동|증강|사람고유` 필드가 없으면 태스크 수 판정을 건너뛴다.

## 알려진 한계: 변이 테스트로 고정 (`mutations.sh`)

점검기가 "살아 있는 팩"과 "구조만 남은 팩"을 얼마나 구별하는지, `examples/after`에 의미만 부순 변이를 넣어 확인했다. 결과는 CI가 고정한다. 한계가 조용히 사라지거나 늘면 실패한다.

| 변이 | 결과 |
| --- | --- |
| 체인 순서 뒤집기(이름은 그대로) | 🔴 게이트가 잡는다 (`next`와 계약 불일치) |
| 정지 지점 스킬이 표에 기록 + 확인 문구 삭제 | 🔴 게이트가 잡는다 |
| 임계값이 문서마다 다름 | 🔴 게이트가 잡는다 |
| 계약의 writers에 한 표가 두 번 | 🔴 게이트가 잡는다. 평가의 오류 주입 시나리오에서 파서가 둘째 줄로 덮어써 "중복"을 "불일치"로 보고하던 것을 고쳤다 |
| 판단기준·예외 절을 모두 삭제(규칙 문장이 하나도 안 남음) | 구조는 통과. `readchk`가 미결(판단기준 없음)로 올린다. 절 하나만 지운 것은 못 본다 |
| 본문을 "아무것도 하지 않는다"로 | **통과한다.** 기계는 본문의 의미를 보지 않는다. 판단기준 없음 미결만 남는다 |

그래서 기계 판정은 "구조·계약 판정"이고, 사람 판정 2개(실제 실행, 오류 주입)가 검증의 나머지 절반이다. 기계 통과를 "동작 확인"으로 적지 않는 이유가 이 표다.

## readchk: 읽은 바를 먼저 적고, 갈래는 하나만 앞세운다 (`readchk.py`)

`DECISIONS.md`에 **이해한 바**(문장으로 재진술)와 **아직 정해지지 않은 것**을 적는다. 미결이 여럿이면 가장 무거운 하나만 앞세운다.
무게 순서: 검수 없음 → 기록자 충돌 → 임계값 상충 → 중간 정지 누락 → 판단기준 없음 → 데이터 미정 → 연동 미정.
판단기준 없음은 자동·증강 스킬의 본문에 `## 판단기준`·`## 예외` 절도, "조건 → 결과" 줄도, 조건문 꼴의 문장(…이면 …한다)도 없을 때 올라온다. 규칙이 불릿으로만 적힌 스킬은 오탐이 날 수 있다. 그때는 절 제목 하나를 붙이면 된다. 게이트와 점검기가 못 보는 자리라 여기서 잡는다.
`결정됨`이 적힌 파일은 덮어쓰지 않고 `DECISIONS.new.md`로 따로 쓴다.

## 규격 동기 (`check_spec_sync.py`)

팩 규격의 정본은 `check/_common.py`의 `SKILL_FIELDS`(`name` · `owner` · `quadrant` · `human` · `inputs` · `outputs` · `reads` · `writes` · `next`), `CONTRACT_KEYS`(`tables` · `writers` · `chain` · `payloads` · `threshold` · `halt_at`), `HUMAN_VALUES`(자동 · 증강 · 사람고유)다. 자기완결 원칙 때문에 `templates/`·`CLAUDE.md`·이 문서가 그것을 재진술하며, 이 가드가 어긋남을 CI에서 잡는다.

## 유사도 감사 (`similarity.py`)

통폐합 후보를 기계적으로 뽑는다. 쌍마다 입출력·표·본문 세 축의 겹침과 같은 문장을 몇 줄 공유하는지를 재고 분류를 **제안**한다:
동일(합침) · 포함(흡수) · 동명이인(입출력 같고 판단기준 다름 → 합치지 않음) · 공통부분(다른 일인데 같은 문장 3줄 이상 → 합치지 않고 `shared/`로 뽑음) · 인접(출력→입력 → 체인) · 무관.
합칠지는 팀이 정한다.

공개 스킬 리포 6개(692개 SKILL.md)로 실측해 더한 규칙: 많은 스킬이 똑같이 가진 줄(생성된 스텁, 공통 머리말)은 리포 공통 틀로 보고 공통 문단 계산에서 뺀다. 틀을 빼면 본문이 3줄 미만인 스킬은 스텁이라 판단을 보류한다. 입출력 필드가 없는 스킬끼리는 같은 문장이 작은 쪽 본문의 90% 이상을 덮을 때만 동일로 본다. 공통 문단 쌍이 20개를 넘으면 가족으로 묶어 "가족마다 참조 파일 하나"로 보고한다. `readchk`는 어느 스킬에도 `next`가 없으면 카탈로그로 보고 흐름·정지 지점 갈래를 내지 않는다.

### 임계값의 근거 (`labels.json` · `calibrate.py`)

상수마다 그 값이 갈라야 하는 실측 쌍이 `check/labels.json`에 이름표로 있다. `python3 check/calibrate.py`가 이름표 쌍을 다시 분류하고, 규칙마다 가장 약한 양성과 가장 강한 음성을 보고한다. 상수는 그 둘 사이에 있어야 하고, 바꾸려면 먼저 반대 사례를 이름표에 더한다. CI가 매번 돌린다.

| 상수 | 값 | 가장 약한 양성 | 가장 강한 음성 | 비고 |
| --- | --- | --- | --- | --- |
| `IO_SAME` 입출력 겹침 | 0.6 | 동일 쌍 1.00 | 체인 쌍 0.25 | "다섯 중 셋이 같다" |
| `TAB_SAME` 표 겹침 | 0.5 | 동일 쌍 1.00 | 동명이인 0.67 (같은 표를 써도 다른 일) | 홀로는 못 가른다. retry-request↔quote-parse는 표가 전부 같아도(1.0) 무관 |
| `TXT_SAME` 동일 vs 동명이인 | 0.3 | 동일 쌍 0.41 | 동명이인 0.24 | 여유 0.17, 쌍 둘뿐. 가설로 두고 실제 팀 팩에서 다시 잰다 |
| `COPY_COVERAGE` 문장 덮임 | 0.9 | 진짜 중복 1.00 | 한 틀로 쓴 다른 스킬 0.77 | 처음 쓴 키워드 겹침 0.8은 그 쌍(0.87)을 동일로 잘못 잡았다 |
| `TXT_READ` 사람이 읽음 | 0.5 | 0.89 | 무관 0.15 (NVIDIA 6만 쌍 99분위 0.39) | 분류가 아니라 "읽어 보라"는 신호 |
| `SHARED_MIN` 같은 문장 줄 수 | 3 | 공통부분 6줄 | 1~2줄 (관용구) | |

점수 가중치(0.45·0.25·0.30)는 표 정렬에만 쓴다. 분류 규칙은 점수를 보지 않는다.

## 흐름 추정 (`flow.py`)

규격(`inputs`·`outputs`·`next`)이 없는 스킬 더미가 어떤 워크플로우를 만들 수 있는지 본문에서 읽는다. 공개 스킬 692개 중 `next`를 쓰는 것은 0개였고, 대신 본문이 서로를 부른다(superpowers 14개 중 7개, NVIDIA 350개 중 250개). 간선마다 근거 문장을 원문 그대로 달고, 근거 없는 간선은 만들지 않는다.

| 관계 | 신호 | 체인에 드는가 |
| --- | --- | --- |
| 선언 | frontmatter `next` | 확정 |
| 입출력 | `A.outputs ∩ B.inputs` | 확정 |
| 순서 | then · after · first · 그다음 · 넘긴 · 끝나면 | 추정. 확인표 C |
| 하위스킬 | invoke · REQUIRED SUB-SKILL · use the X skill · 호출 | 추정. 확인표 C (A 안에서 B를 부르는 한 걸음) |
| 선행지식 | REQUIRED BACKGROUND · must understand · 먼저 알아야 | 체인 아님. 읽을 순서 |
| 언급 | 그 밖의 이름 부름, 나열(examples · 와 달리 · ✅/❌ 서식 예) | 간선 아님. 보고만 |

근거는 `check/flow_labels.json`이다. obra/superpowers 14개를 사람이 읽고 정한 기대 간선 11개를 `--labels`로 대조하면 맞음 11 · 더 잡음 0 · 놓침 0이다. 처음 판에서 틀렸던 것 둘을 그 이름표가 고정한다: 예시 나열 안의 이름을 순서로 잡던 것("Examples: TDD, verification-before-completion"), 서식 예시(`✅ Good:`) 안의 REQUIRED SUB-SKILL을 진짜 관계로 잡던 것. 저장소 안 근거는 `examples/prose/`다.

추정 간선은 `intake`가 확인표 C에 `(추정)`으로 올리고, `askflow`가 통째로 확인받고, 사람이 확인한 것만 `weave`가 `chain`에 넣는다. 추정인 채로 계약에 들어간 간선은 거짓 계약이다. 알려진 한계: 순서 단어가 없는 문장의 진짜 간선은 놓친다(superpowers의 `subagent-driven-development → requesting-code-review`). "불려도 폴더에 없는 스킬"은 문장 꼴로 잡으므로 일반 명사가 섞일 수 있어 보고만 한다.

## 스킬 평가 (`skills/*/*/evals/evals.json`)

스킬마다 시나리오 3개 이상이 [skill-creator](https://github.com/anthropics/skills/tree/main/skills/skill-creator)의 `evals.json` 서식(`prompt` · `files` · `expected_output` · `expectations`)으로 있다. 입력은 `examples/`와 `evals/files/`의 고정 자료다. 실행은 skill-creator의 방식 그대로: 시나리오마다 스킬을 읽은 실행과 읽지 않은 실행(baseline)을 같은 모델로 돌리고, `expectations`를 하나씩 채점해 `grading.json`으로 남긴다. 채점 결과와 배운 것은 `planning/progress.md`의 Test Results 표에 적는다. 이 평가는 기계 판정(L0~L4)이 못 보는 것, 즉 스킬 지시문을 읽은 에이전트가 실제로 멈추고 묻고 지어내지 않는지를 본다.

## 판정 철학 (paperthin)

- 점검기는 통과시키기 위해서가 아니라 **탈락시키기 위해** 존재한다.
- 검사 항목을 늘리기 전에, 그 항목이 실패를 실제로 잡아낸 적이 있는지 먼저 묻는다 (제거 우선).
- 기계 판정이 통과해도 사람 판정 없이 "동작 확인"이라고 적지 않는다 (자기 확인 금지).
