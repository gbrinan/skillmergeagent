사용자가 순서를 설계하게 하지 않고, 답에서 다음 초안을 만들어 확인한다.

## Goal

업무 설명 한 줄부터 시작해 시작 조건, 단계별 입출력·담당, 분기·예외, 완료 기준이 이어지는 워크플로우를 만든다. 자료에 있는 사실을 다시 묻지 않고, 업무와 무관한 서식을 채우느라 인터뷰를 늘리지 않는다.

## Workflow

1. 요청·이전 답·자료·기존 기획서를 먼저 읽는다. `intake`가 없으면 직접 파악한다. 파일이 없거나 접근할 수 없어도 대화만으로 시작하며 파일 제출을 전제하지 않는다. 빈 스킬 카드나 확인표 세 개를 만들지 않는다.
2. 아래 정보를 값·상태·출처로 정리한다. 상태는 **확정**(사용자 답 또는 명시된 자료), **추정**(제안), **미확인**(필요하나 모름), **해당 없음**(이 업무에 불필요), **충돌**(근거가 다름)이다. 파일에 없다는 이유로 해당 없음으로 바꾸지 않는다.

   | 정보 | 알아야 할 것 | 필요한 시점 |
   | --- | --- | --- |
   | 목적·범위 | 누가 어떤 일을 줄이고, 무엇은 하지 않는가 | 첫 초안 |
   | 시작·입력 | 언제 시작하고 무엇을 어디서 받는가 | 첫 초안 |
   | 결과·완료 기준 | 누구에게 무엇을 주면 끝이며 무엇으로 맞음을 판단하는가 | 첫 초안 |
   | 단계·담당 | 현재 절차, 쓸 수 있는 스킬, 사람/AI의 역할과 전달물 | 흐름 확정 |
   | 판단·예외 | 경로를 가르는 조건, 정보 누락/실패 시 처리, 확인하고 멈출 곳 | 흐름 확정 |
   | 환경·권한 | 사용 도구·접근 가능 여부, 저장/발송 범위, 시간·비용 제약 | 관련 단계 확정; 실제 접근은 실행 전 |
   | 데이터 구조 | 표/DB를 실제로 쓰면 이름·필요 필드·원본·기록 담당 | 해당 업무만 |

3. **질문은 다음 결정을 막는 것 하나만** 고른다. 목적을 모르면 “가장 먼저 줄이고 싶은 반복 업무는 무엇인가요?”로 시작한다. 목적을 알면 결과 → 시작/입력 → 순서/담당 → 판단/예외 → 필요한 환경 순으로 빈틈을 본다. 충돌이 결과나 권한을 바꾸면 먼저 해결한다. 고정 질문 수나 모든 항목의 순회는 없다.
4. 매 턴 확정된 내용·달라진 초안을 3줄 이내로 보여 주고, 질문이 설계의 어디를 바꾸는지 한 문장으로 설명한다. 자료에 근거한 선택지 2~3개와 직접 답할 여지를 주되, 근거가 없으면 짧은 자유 답변을 받는다. 확인 질문도 그 턴의 질문 하나에 포함한다. 이미 답한 값은 다시 확인받지 않는다.
5. 목적·입력·결과가 잡히면 순서를 몰라도 **추정 초안**을 먼저 그린다. 단계마다 입력 → 할 일 → 출력과 담당(기존 스킬/사람/미구현)을 붙인다. 사용자가 “모르겠다”고 하면 가능한 절차와 차이를 제안해 선택받는다. 같은 항목을 두 번 답하기 어렵거나 사용자가 미루면 미확인으로 남기고 독립적인 부분을 계속한다. 중요한 규칙은 삭제하지 않고 해당 단계의 실행을 보류한다.
6. 기존 스킬은 목적에 필요한 것만 연결한다. 입출력 이름 겹침과 본문의 순서·호출은 후보 근거이며, 의미·필수 입력 충족·분기 조건을 확인한다. 확인표 C가 있으면 미확인 간선만 묶어 확인한다. 하위 호출은 부모 단계 안에, 병렬은 합류 조건과 함께 적는다. 없는 스킬은 사람 작업인지 미구현인지 묻고, 새 파일이나 실행 능력을 지어내지 않는다.
7. 답을 받을 때마다 `agent-plan.md`의 해당 값을 고친다. 없다면 첫 초안부터 만들고, 파일을 쓸 수 없으면 대화에 같은 내용을 낸다. 기존 planning 파일이 있으면 진행만 기록하고 업무 사실은 기획서를 가리킨다. 재개 시 기획서의 미확인·충돌·마지막 질문에서 이어간다.
8. **산출**: 기본은 짧은 기획서 하나다. 목적/범위, 시작/입력/결과/완료 기준, 단계 표(담당·입력·행동·출력·다음 조건), 예외/정지, 환경, 미결과 다음 질문을 담는다. 표가 없는 업무는 문서·메시지·파일 전달로 표현한다. 사분면과 폴더 트리는 사용자 질문이 아니라 패키징 시 정할 구현 사항이다. 명시적으로 실행 팩·계약을 요청했거나 기존 팩을 수정할 때만 8절 서식과 `CONTRACT.md`를 쓴다. 서식이 없어도 같은 내용을 직접 작성한다. 계약에는 확정된 이름·간선만 넣고 미결은 기획서에 남긴다.
9. **종료**: 모든 필수 입력의 공급처, 단계 담당/능력, 분기·예외·정지, 결과 확인 기준이 정해지면 “설계 완료, 실행 미검증”으로 전달한다. 필요 없는 환경 세부는 더 묻지 않는다. 필요한 결정이 남으면 “초안”으로 전달하고 다음 질문 하나를 남긴다. 실제 실행을 요청받으면 정상 입력과 누락/잘못된 입력으로 확인하고 관찰 결과를 기록한다. 체크리스트만 만든 것은 실행 검증이 아니다.

## Rules

산출물을 전달하는 종료점에서 생성 후 정리 훅이 설치돼 있으면 `docs/post-generation-hook.md`에 따라 실제 세션 ID와 이번 생성 파일만 등록한다. 문답 중간·승인 대기·재검토 중에는 등록하지 않는다. 훅이 없으면 목적 대비 불필요함과 중복 사실을 한 차례 직접 감사하고, 수정안은 승인 뒤 반영한다. 자동 훅 미등록을 숨기지 않는다.

- 사실과 제안을 구분한다. 침묵·“알아서”·선택지 기본값은 추정이나 권한의 확정이 아니다.
- 해당 없음은 질문 목록에서 제외한다. 표가 없다고 표를 만들거나 칸 이름을 묻지 않는다.
- 충돌한 예외·판단기준·책임은 보존하고 보류한다. 제거는 불필요함이 확인된 항목에만 적용한다.
- 설계 승인과 실제 파일 병합·발송·배포 권한을 구분한다. 기존 원본 변경은 요청 범위와 승인에 따른다.
- 기획서의 현재 값이 정본이다. 변경 이력을 본문에 덧붙이거나 별도 답변 장부로 복제하지 않는다.

## Verification

1. 자료 없이 시작하고, 알려진 값과 해당 없는 항목은 재질문하지 않았다.
2. 턴마다 질문이 최대 하나이며, 답을 반영한 흐름이 진전됐다.
3. 단계별 전달물이 이어지고, 없는 능력·분기·권한을 확정 사실로 쓰지 않았다.
4. 미결·충돌·재개할 질문이 보존되고, 설계 완료와 실행 검증의 상태를 구분했다.
